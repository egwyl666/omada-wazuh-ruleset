# Omada -> Wazuh ruleset

[English version: README.md](README.md)

Правила виявлення для логів клієнтського трафіку **TP-Link Omada** (точки доступу EAP / контролер) у **Wazuh SIEM**.
Omada пише по одному запису на кожен мережевий потік. Цей проєкт декодує такі записи і перетворює їх на алерти:
підозрілі порти, збіги з threat intel, невідомі пристрої, латеральний рух із Wi-Fi, сканування, віддалений доступ у неробочий час тощо.

Інструкцію написано для **SOC-аналітика з обмеженим доступом**: ви працюєте в **дашборді Wazuh**, а все на серверах
(Omada, rsyslog, ОС менеджера Wazuh) робиться **за заявкою** командам, які ними володіють. Готові тексти заявок у
[Додатку A](#додаток-a-шаблони-заявок). **Скрипти не обов'язкові**: кожен крок це або дія в UI, або заявка.
Опційне автоматичне оновлення списків threat intel, яке адмін встановлює один раз, лежить в `optional/ti-auto-update/` ([розділ 7.4](#74-опційно-автоматичне-оновлення-адмін-встановлює-один-раз)).

Структура репозиторію:

| Шлях | Що це |
|---|---|
| `decoders/omada_decoders.xml` | Декодер: розбирає рядок логу на поля |
| `rules/omada_rules.xml` | 86 активних правил (+ 1 вимкнене, 100505), ID 100500-100850 |
| `lists/private-ips`, `lists/telegram-ips` | CDB-списки: внутрішні префікси, підмережі Telegram |
| `lists/known-macs`, `lists/known-aps` | CDB-списки: дозволені клієнтські пристрої та точки доступу (заповнюєте ви; `known-aps` опційний) |
| `lists/ti-feodo-c2`, `lists/ti-tor-relays`, `lists/ti-mining-pools` | CDB-списки threat intel. Постачаються як **заглушки**; заповнюєте вручну (розділ 7) |
| `docs/mining-pools.txt` | Довідковий список доменів майнінг-пулів для збирання `ti-mining-pools`; у Wazuh **не** розгортається |
| `docs/CHANGELOG_UA.md` | Історія змін (українською) |
| `optional/ti-auto-update/` | **Опційно.** Два скрипти і чотири юніти systemd, що автоматично оновлюють списки threat intel (розділ 7.4) |

Усе з `lists/` розгортається на менеджер; з `docs/` нічого; `optional/` лише якщо ви вирішите ним користуватися.

> Важливо: правила написано за описом формату логів Omada. Перш ніж покладатися на них у production, виконайте перевірки з
> [розділу 10](#10-тестування-правил) та [розділу 12](#12-обмеження-і-що-перевірити-в-logtest).

## 1. Що це і навіщо

Omada дає IP джерела й призначення, порти, протокол та MAC клієнта і AP. Вона **не** дає вміст пакетів, байти, URL та
вердикт allow/deny. Тому виявлення будується на тому, **хто, з ким, на який порт, як часто і коли** спілкується.

| Група | ID правил | Level | Що виявляє |
|---|---|---|---|
| Базове | 100500 | 0 | Будь-який декодований потік Omada (батько всіх правил) |
| Інвентаризація | 100505 (вимк.), 100506, 100507 | 10 / 7 / 7 | Невідома AP (вимкнено за замовчуванням), новий невідомий пристрій, новий пристрій із рандомізованим MAC |
| Поділ за призначенням | 100510, 100511 | 0 | Зовнішнє чи внутрішнє призначення (через `private-ips`) |
| Threat intel | 100512-100514 | 12 / 10 / 10 | Призначення: відомий C2 ботнету (Feodo), реле Tor або майнінг-пул |
| Анонімайзери / C2 / майнери (порти) | 100520-100524 | 10, 10, 10, 8, 6 | Порти Tor, reverse shell/C2, stratum майнінгу, IRC, SOCKS/HTTP-проксі |
| Віддалений доступ (зовнішній) | 100530-100534 | 8, 8, 9, 4, 7 | Вихідні RDP, VNC, Telnet, SSH, TeamViewer/AnyDesk/RustDesk |
| Ризиковані протоколи (зовнішні) | 100540-100545 | 9, 8, 5, 8, 7, 6 | SMB/NetBIOS/RPC, прямий SMTP, FTP, TFTP, SNMP/LDAP, порти баз даних в інтернет |
| Обхід DNS | 100550-100551 | 4, 5 | Прямий DNS на зовнішні резолвери, DNS-over-TLS |
| VPN / тунелі | 100560 | 5 | OpenVPN, WireGuard, PPTP, L2TP, IPsec |
| P2P / торрент | 100570-100571 | 5 | Порти призначення / джерела BitTorrent |
| Латеральний рух (внутрішній) | 100590-100596 | 6, 6, 8, 6, 6, 7, 7 | Wi-Fi клієнт до SMB, RDP, WinRM, RPC, VNC, Telnet, баз даних |
| Кореляція | 100600-100604 | 10, 12, 8, 12, 10 | Сканування портів, внутрішній sweep, підтверджений торрент, повторний трафік до C2/майнерів, спамбот |
| Аномалії частоти | 100620-100621 | 7, 9 | 200+ / 1000+ подій за хвилину на один dst:port |
| Неробочий час | 100630-100633 | 10, 9, 8, 7 | Віддалений доступ / VPN уночі (20:00-07:00) та у вихідні: та сама подія з вищим level |
| Застосунки (зовнішні) | 100700-100754 | 0-7 | Web, Telegram, push, дзвінки, ігри, стрімінг, sync, IoT, віддалений робочий стіл. Здебільшого level 0-4 (видимість), 100754 має 7 |
| Шум LAN (внутрішній) | 100800-100806 | 0 (100805: 3) | DNS/DHCP/Kerberos, mDNS/SSDP, друк, AirPlay, внутрішній web, SSH, Syncthing |

За замовчуванням Wazuh зберігає лише алерти level 3 і вище, тож події level 0-2 у дашборді не видно.

## 2. Вимоги

- **Wazuh 4.3 або новіший** (декодер використовує PCRE2; кореляція використовує `same_field` / `different_*`). Якщо дашборд не показує версію
  (зазвичай у меню, *About*), запитайте в адміна Wazuh.
- **Логи Omada через syslog**, доставлені у файл, який читає менеджер Wazuh (або агент). Див. розділ 5 і заявки A1-A3.
- **Права в дашборді**, в ідеалі: перегляд алертів, *Ruleset Test*, редагування rules / decoders / CDB lists, редагування конфігурації, рестарт.
  Без прав на редагування все одно все працює через заявки A3/A5.
- Годинник і часовий пояс менеджера мають бути правильні (правила неробочого часу беруть локальний час менеджера). Заявка A4.
- Для ручного оновлення threat intel (розділ 7): робоча станція з доступом в інтернет і або Unix-подібна оболонка (Linux, macOS, WSL),
  або PowerShell.

## 3. Приклад логу та розбір полів

```
[1791521490.308231667] AP MAC=00:11:22:33:44:55 MAC SRC=00:11:22:33:44:66 IP SRC=192.0.2.40 IP DST=149.154.167.41 IP proto=6 SPT=55138 DPT=443
```

| Поле Wazuh | Звідки | Приклад | Значення |
|---|---|---|---|
| `omada.epoch` | `[...]` | `1791521490.308231667` | Unix-час із дробовою частиною. Необов'язкове: є не в кожному записі |
| `omada.ap_mac` | `AP MAC=` | `00:11:22:33:44:55` | Точка доступу, через яку пройшов трафік |
| `omada.src_mac` | `MAC SRC=` | `00:11:22:33:44:66` | Клієнтський пристрій (ключ для інвентаризації та P2P-кореляції) |
| `srcip` | `IP SRC=` | `192.0.2.40` | IP клієнта |
| `dstip` | `IP DST=` | `149.154.167.41` | IP призначення |
| `protocol` | `IP proto=` | `6` | Номер IP-протоколу: 6 = TCP, 17 = UDP |
| `srcport` | `SPT=` | `55138` | Порт джерела (зазвичай ефемерний) |
| `dstport` | `DPT=` | `443` | Порт призначення; на нього спираються більшість правил |

У дашборді та в алертах ці поля мають вигляд `data.omada.src_mac`, `data.omada.ap_mac`, `data.srcip`, `data.dstip`, `data.dstport` тощо.

## 4. Встановлення

Спочатку налаштуйте приймання логів (розділ 5): без логів перевірити можна лише в *Ruleset Test*.
ID правил 100500-100850 не повинні збігатися з іншими власними правилами на менеджері; перевірте на сторінці Rules і перенумеруйте, якщо збігаються.

### 4.1 Через дашборд (ваша роль може редагувати ruleset)

1. **Декодер.** *Decoders* -> *Custom decoders* -> додати / імпортувати файл -> `omada_decoders.xml` (вміст з `decoders/`). Зберегти.
2. **Правила.** *Rules* -> *Custom rules* -> додати / імпортувати файл -> `omada_rules.xml` (вміст з `rules/`). Зберегти.
3. **CDB-списки.** *CDB lists* -> додати / імпортувати кожен файл з `lists/` **з точно такою самою назвою** (без розширення):
   `private-ips`, `telegram-ips`, `known-macs`, `known-aps`, `ti-feodo-c2`, `ti-tor-relays`, `ti-mining-pools`.
   Після збереження відкрийте кожен список і перевірте, що рядки виглядають точно як у репозиторії (для MAC-списків: `"aa:bb:cc:dd:ee:ff":name`, з лапками).
4. **Зареєструйте списки.** Відкрийте конфігурацію менеджера (*Settings* -> *Edit configuration*, `ossec.conf`) і переконайтеся, що ці рядки
   стоять **всередині наявного блоку `<ruleset>`**. Дашборд не завжди додає їх сам під час створення списку:

   ```xml
   <list>etc/lists/private-ips</list>
   <list>etc/lists/telegram-ips</list>
   <list>etc/lists/known-macs</list>
   <list>etc/lists/known-aps</list>
   <list>etc/lists/ti-feodo-c2</list>
   <list>etc/lists/ti-tor-relays</list>
   <list>etc/lists/ti-mining-pools</list>
   ```

5. **Джерело логів.** У тій самій конфігурації додайте блок `<localfile>` з розділу 5.2 (якщо Linux-адмін ще не додав).
6. **Рестарт** менеджера з дашборду (він пропонує рестарт після збереження, або кнопка рестарту на сторінці конфігурації / статусу).
   Дашборд перевіряє конфігурацію перед рестартом; якщо він показує помилку, спершу виправте її.
   Рестарт ненадовго зупиняє аналіз; узгодьте момент із командою.
7. **Перевірте** в *Ruleset Test* (розділ 10).

Файли, збережені через дашборд, автоматично отримують правильного власника; `chown` не потрібен.

### 4.2 Через заявку (немає прав на редагування)

Надішліть **заявку A3**, додавши репозиторій (або zip). У ній точні команди для адміна.
Потім перевірте в *Ruleset Test* (розділ 10).

## 5. Приймання логів: Omada -> rsyslog -> файл -> Wazuh

Цю частину роблять інші команди: **A1** для мережевої команди, **A2** для Linux-адміна і частина `<localfile>` із **A3**.
Конфігурації нижче ви додаєте до цих заявок.

### 5.1 rsyslog на менеджері Wazuh

`/etc/rsyslog.d/10-omada.conf`:

```
# НЕ перетворювати керівні символи на #015 / #012 (див. нижче)
global(parser.escapeControlCharactersOnReceive="off")

module(load="imudp")
input(type="imudp" port="514" ruleset="omada")
# Для TCP замість UDP або разом із ним:
# module(load="imtcp")
# input(type="imtcp" port="514" ruleset="omada")

template(name="omada_raw" type="string" string="%msg%\n")

ruleset(name="omada") {
    action(type="omfile" file="/var/log/omada/omada.log" template="omada_raw")
    stop
}
```

Плюс: `mkdir -p /var/log/omada`, `systemctl restart rsyslog`, фаєрвол пропускає UDP/TCP 514 від контролера / AP Omada,
і правило logrotate для `/var/log/omada/omada.log`.

**Проблема `#015#012`.** Omada може пакувати кілька записів в одне syslog-повідомлення, розділяючи їх CR+LF.
За замовчуванням rsyslog екранує керівні символи, тому роздільники стають буквальним текстом `#015#012` (вісімкове 015 = CR, 012 = LF),
і Wazuh бачить один величезний рядок зі склеєними записами; декодується тільки перший запис.
`parser.escapeControlCharactersOnReceive="off"` вимикає екранування, тож у файлі з'являються справжні переноси рядків і кожен запис
стає окремим рядком. Розпізнати проблему в дашборді: подій Omada набагато менше, ніж очікувалося, а в *Ruleset Test* рядок-зразок
від адміна містить `#012`.

### 5.2 Wazuh `<localfile>`

В `ossec.conf` менеджера (або агента на хості, де лежить файл):

```xml
<localfile>
  <log_format>syslog</log_format>
  <location>/var/log/omada/omada.log</location>
</localfile>
```

Потім рестарт.

## 6. Як знайти все, що потрібно

**Чи надходять події Omada?** У дашборді (*Threat Hunting* / *Discover*) запит `rule.groups: omada` за останню годину.
Оскільки зберігається лише level 3+, ви побачите Telegram, віддалений доступ, нові пристрої тощо, а не кожен потік. Якщо після
робочого дня немає нічого, перевірте заявкою A6, що файл пишеться, і заявкою A7, чи немає помилок.

**MAC клієнтських пристроїв** (для `known-macs`):

- кожен новий пристрій дає один алерт 100506/100507, тож зробіть запит `rule.id: (100506 or 100507)` і побудуйте таблицю
  (*Visualize* -> *Data table*, split rows за *Terms* по `data.omada.src_mac`, size 500; додайте колонки `data.srcip` і `data.omada.ap_mac`);
- або попросіть повний список із сирого логу **заявкою A6**.

**MAC власних AP** (опційно, потрібні лише для правила 100505; див. [розділ 8](#8-точки-доступу-known-aps-і-правило-100505-опційно-вимкнено-за-замовчуванням)):
та сама таблиця з *Terms* по `data.omada.ap_mac` для `rule.groups: omada`, або заявка A6.

**Формат запису в CDB.** Один запис на рядок, MAC у подвійних лапках (у ньому є двокрапки), далі `:` і мітка:

```
"aa:bb:cc:dd:ee:ff":my-laptop
```

MAC у логах у нижньому регістрі; у списках теж пишіть у нижньому (пошук чутливий до регістру).
CDB-файл не може бути порожнім. `known-macs`, `known-aps` і списки `ti-*` постачаються з рядком-заглушкою.

**Де лежать файли на менеджері** (для заявок і для адміна; у дашборді ви бачите ті самі файли за назвою):

| Що | Шлях |
|---|---|
| Головний конфіг | `/var/ossec/etc/ossec.conf` |
| Власні правила | `/var/ossec/etc/rules/` |
| Власні декодери | `/var/ossec/etc/decoders/` |
| CDB-списки | `/var/ossec/etc/lists/` |
| Лог менеджера (помилки старту) | `/var/ossec/logs/ossec.log` |
| Алерти (JSON) | `/var/ossec/logs/alerts/alerts.json` |

**Часовий пояс менеджера.** Правила неробочого часу 100630-100633 беруть локальний час менеджера і написані під `Europe/Kyiv` (раніше `Europe/Kiev`).
У дашборді його надійно не видно; запитайте **заявкою A4**.

**Де дивитися алерти.** Дашборд, *Threat Hunting* / *Security events*. Корисні фільтри:
`rule.groups: suspicious_port`, `threat_intel`, `inventory`, `new_device`, `off_hours`, `lateral`, `scan`, `p2p`, `remote_access`,
`policy_violation`, `anomaly`, `app_gaming`, або `rule.id: 100506`. Фільтр за пристроєм: `data.omada.src_mac: "00:11:22:33:44:66"`.

## 7. Threat intel: ручне оновлення (за замовчуванням) або автоматичне (опційно)

Правила 100512-100514 перевіряють IP призначення за трьома CDB-списками **до** правил за портами.
Списки постачаються як заглушки (`0.0.0.0:placeholder-replace-me`), тож правила завантажуються, але не спрацюють, доки ви їх не заповните.
Два способи тримати їх заповненими: **вручну** (7.1-7.3, на сервері нічого не потрібно) або **автоматично** (7.4, адмін встановлює один раз).

| Список | Джерело | Правило | Level |
|---|---|---|---|
| `ti-feodo-c2` | abuse.ch Feodo Tracker, список "recommended" (C2 ботнетів, мало хибних спрацювань, CC0): https://feodotracker.abuse.ch/downloads/ipblocklist_recommended.txt | 100512 | 12 |

### 7.1 Зберіть файли на робочій станції

Кожен рядок має бути `IP:назва-списку`, переноси LF, файл не порожній. Запускайте в порожній теці; спершу скопіюйте туди `docs/mining-pools.txt`.

**Linux / macOS / WSL** (потрібні `curl`, `grep`, `sed`; для пулів `getent` на Linux або `dig` деінде):

```bash
IPRE='([0-9]{1,3}\.){3}[0-9]{1,3}'

# Feodo. Файл має переноси CRLF: tr -d '\r' обов'язковий, інакше жоден IP не підійде.
curl -fsS https://feodotracker.abuse.ch/downloads/ipblocklist_recommended.txt | tr -d '\r' \
  | grep -E "^$IPRE$" | sort -u | sed 's/$/:ti-feodo-c2/' > ti-feodo-c2

# Реле Tor (лише IPv4)
curl -fsS 'https://onionoo.torproject.org/summary?type=relay&running=true' \
  | grep -oE "$IPRE" | sort -u | sed 's/$/:ti-tor-relays/' > ti-tor-relays

# Майнінг-пули (на macOS замініть рядок getent на: dig +short A "$d")
CF='^(104\.(1[6-9]|2[0-7])\.|172\.(6[4-9]|7[01])\.|162\.15[89]\.|188\.114\.(9[6-9]|10[0-9]|11[01])\.|141\.101\.|108\.162\.|198\.41\.)'
grep -vE '^\s*(#|$)' mining-pools.txt | while read -r d; do
  getent ahostsv4 "$d" | awk '{print $1}'
done | grep -E "^$IPRE$" | grep -vE "$CF" | sort -u | sed 's/$/:ti-mining-pools/' > ti-mining-pools

wc -l ti-*
```

**Windows PowerShell** (той самий результат; у цьому репозиторії не тестувалося, тож перевірте результат за 7.2):

```powershell
$ipre = '^\d{1,3}(\.\d{1,3}){3}$'
function Save-Cdb($name, $ips) {
  $lines = $ips | Where-Object { $_ -match $ipre } | Sort-Object -Unique | ForEach-Object { "$($_):$name" }
  if (-not $lines) { $lines = @('0.0.0.0:placeholder-replace-me') }
  [IO.File]::WriteAllText("$PWD\$name", (($lines -join "`n") + "`n"))   # LF endings
}

$feodo = (Invoke-WebRequest -UseBasicParsing 'https://feodotracker.abuse.ch/downloads/ipblocklist_recommended.txt').Content -split "`r?`n"
Save-Cdb 'ti-feodo-c2' $feodo

$tor = (Invoke-RestMethod 'https://onionoo.torproject.org/summary?type=relay&running=true').relays | ForEach-Object { $_.a }
Save-Cdb 'ti-tor-relays' $tor

$cf = '^(104\.(1[6-9]|2[0-7])\.|172\.(6[4-9]|7[01])\.|162\.15[89]\.|188\.114\.(9[6-9]|10[0-9]|11[01])\.|141\.101\.|108\.162\.|198\.41\.)'
$pools = Get-Content .\mining-pools.txt | Where-Object { $_ -notmatch '^\s*(#|$)' } | ForEach-Object {
  Resolve-DnsName $_ -Type A -ErrorAction SilentlyContinue | Where-Object Type -eq 'A' | ForEach-Object IPAddress
} | Where-Object { $_ -notmatch $cf }
Save-Cdb 'ti-mining-pools' $pools
```

### 7.2 Перевірте перед завантаженням

- `ti-tor-relays` має містити **тисячі** рядків (приблизно 6-8 тисяч). Кілька десятків означає, що завантаження зламалось: не завантажуйте, лишіть старий список.
- `ti-feodo-c2` малий за природою (іноді один-два рядки). Відкрийте джерело в браузері й подивіться `Last updated` у заголовку:
  якщо дата кількамісячної давнини, стрічка застаріла і користі від списку мало; вирішіть, чи варто його підтримувати.
- `ti-mining-pools`: десятки рядків. Якщо порожній, не спрацював DNS (корпоративний DNS може блокувати домени пулів; попросіть виняток або резолвте деінде).
- Якщо файл вийшов порожнім, впишіть у нього рядок-заглушку `0.0.0.0:placeholder-replace-me`: порожній CDB-файл це помилка.
- Рядки мають виглядати як `198.51.100.7:ti-tor-relays`: без пробілів і заголовків.

### 7.3 Завантаження і застосування

- **Дашборд:** *CDB lists* -> відкрити список -> замінити вміст (або імпортувати файл з тією самою назвою) -> зберегти -> рестарт.
- **Немає прав:** надішліть **заявку A5** з файлами.

Wazuh компілює CDB-списки лише під час старту менеджера, тому **новий вміст діє тільки після рестарту**. Рестарт ненадовго зупиняє
аналіз подій і скидає лічильники кореляційних правил у пам'яті (сканування, торрент, спамбот, частота). Об'єднуйте оновлення списків
(threat intel, `known-macs`, `known-aps`) в один рестарт в узгоджене тихе вікно.

Рекомендований ритм: Tor і Feodo раз на тиждень-два, пули щомісяця або коли змінюєте `docs/mining-pools.txt`. Застарілі списки здебільшого
означають пропущені виявлення; реле Tor змінюються постійно, тож старий список Tor також дає трохи хибних спрацювань на перевикористаних IP.

### 7.4 Опційно: автоматичне оновлення (адмін встановлює один раз)

Якщо не хочете повторювати 7.1-7.3, попросіть адміна встановити файли з `optional/ti-auto-update/` (**заявка A8**).
Це не обов'язково: набір правил працює так само і без нього. Оновлюються `ti-feodo-c2`, `ti-tor-relays`, `ti-mining-pools` і
`telegram-ips`; `known-macs`, `known-aps`, `private-ips`, правила і декодери ніколи не змінюються.

**Як це працює: дві частини, кожна з мінімальними правами.**

| Юніт | Від кого | Мережа | Може писати в | Що робить |
|---|---|---|---|---|
| `omada-ti-fetch.timer` | systemd | | | Щоночі о 04:15 (+ до 10 хв випадкової затримки) запускає частину fetch |
| `omada-ti-fetch.service` -> `omada-ti-fetch.sh` | окремий користувач `omada-ti`, без capabilities, система лише для читання | так | лише `/var/lib/omada-ti` | Завантажує Feodo, Tor, Telegram, резолвить домени пулів, перевіряє розміри, пише підготовлені списки і файл-прапорець `ready` |
| `omada-ti-apply.path` | systemd | | | Запускає частину apply, щойно з'являється `ready` |
| `omada-ti-apply.service` -> `omada-ti-apply.sh` | root | **ні** (`PrivateNetwork`) | `/var/ossec/etc/lists`, `/var/lib/omada-ti`, `/var/backups/omada-ti` (+ робочі каталоги Wazuh для перевірки конфігурації) | Суворо перевіряє кожен підготовлений список, встановлює лише змінені (з резервною копією), виконує `wazuh-analysisd -t`, перезапускає `wazuh-manager`. Якщо перевірка не пройшла: відновлює копії, **рестарту немає** |

Код, що ходить в інтернет, ніколи не працює з привілеями і не має доступу до Wazuh; частина від root ніколи не ходить у мережу і
приймає лише файли, що виглядають точно як CDB-списки IP (усе інше відкидається і логується).

**Поведінка, про яку варто знати:**

- Зламане джерело (помилка завантаження, Tor менше 1000 записів, жоден пул не зарезолвився) пропускається: список у Wazuh лишається
  як був, а юніт fetch завершується як *failed*, тож моніторинг адміна це побачить.
- **Рестарт лише якщо список змінився.** Список Tor змінюється майже щодня, тож очікуйте короткий рестарт `wazuh-manager` більшість ночей
  між 04:15 і приблизно 04:30. Якщо це надто часто, запускайте щотижня (див. налаштування нижче).
- DNS пулів працює за round-robin і щоразу повертає іншу підмножину IP. Щоб список (і рестарт) не змінювався щоночі, IP пулу
  лишається в списку 30 днів після останнього резолву (`POOLS_KEEP_DAYS`).
- `Persistent=false`: якщо сервер був вимкнений о 04:15, цей запуск пропускається, а не виконується (з рестартом Wazuh) після завантаження вдень.
- Він перезаписує `telegram-ips`. Якщо ведете цей список вручну, приберіть його з `FETCH_LISTS` (див. налаштування).

**Встановлення (адмін, від root, з кореня репозиторію):**

> `ReadWritePaths=` через `systemctl edit omada-ti-apply.service`.

## 8. Точки доступу (`known-aps`) і правило 100505: опційно, вимкнено за замовчуванням

**Що таке `known-aps`.** Білий список MAC **точок доступу**: значення `AP MAC=` у логу, тобто EAP, через яку пройшов трафік клієнта.
Це **не** список контролерів. Контролер Omada (software controller, OC200/OC300) лише керує AP і пересилає їхні логи;
його власний MAC ніколи не з'являється в `AP MAC=`, тому контролер у цей список не заносять.

**Хто його використовує.** Лише правило 100505 (rogue AP, level 10): "цей потік пройшов через AP, якої немає в `known-aps`". Жодне інше правило список не читає.

**Чи працює воно зараз? Ні, і від нього нічого не залежить.** 100505 закоментоване, тож список не перевіряється. Він містить заглушку
лише для того, щоб запис `<list>etc/lists/known-aps</list>` вказував на наявний непорожній файл. Усі інші правила працюють, не знаючи
жодної AP. **Встановлюйте все і залиште `known-aps` як є.**

**Чому вимкнено за замовчуванням.** Якби 100505 було ввімкнене з порожнім або неповним списком, під нього потрапляв би **кожен потік** через "невідому" AP.
Оскільки перемагає лише перше правило серед сусідніх (100505 перевіряється до поділу за призначенням), такі потоки ще й перестали б
доходити до правил за портами і threat intel. Тому вмикайте його лише з повним списком, а нові AP додавайте до списку **до** їх запуску.

### Підключення AP пізніше

1. **Знайдіть MAC AP.** Будь-яким способом:
   - таблиця в дашборді з *Terms* по `data.omada.ap_mac` (розділ 6);
   - інтерфейс контролера Omada, список *Devices* (колонка MAC), якщо доступ є у вас або в мережевої команди;
   - заявка A6 (повний список із сирого логу з кількістю потоків на кожну AP).

   MAC, який не вдається зіставити зі справжньою AP, це саме те, що правило має ловити: розберіться з ним, перш ніж додавати.

2. **Складіть список** (нижній регістр, одна AP на рядок, рядок-заглушку видаліть):

   ```
   "aa:bb:cc:dd:ee:01":office-floor1
   "aa:bb:cc:dd:ee:02":office-floor2
   ```

3. **Завантажте** його в CDB-список `known-aps` у дашборді (або заявка A5).

4. **Увімкніть правило.** У дашборді відкрийте власний файл правил `omada_rules.xml`. Правило 100505 загорнуте в коментар, перший і
   останній рядки якого містять маркер `ENABLE-100505`. Видаліть **обидва** ці рядки (і нічого більше), збережіть.
   Без прав на редагування: заявка A5 просить адміна виконати `sed -i '/ENABLE-100505/d' /var/ossec/etc/rules/omada_rules.xml`.

5. **Рестарт**, потім перевірка в *Ruleset Test*: рядок з `AP MAC=`, що є в `known-aps`, **не** має давати 100505;
   той самий рядок з будь-яким іншим MAC AP має давати 100505, level 10.

**Додати AP пізніше:** додайте її рядок у `known-aps`, рестарт, потім вмикайте AP.
**Вимкнути знову:** поверніть два рядки-маркери або замініть файл правил версією з цього репозиторію, потім рестарт.

> Примітка: логи потоків, на яких побудовано правила, зібрано через контролер Omada. Чи надсилають AP у standalone-режимі (без контролера)
> такі самі записи `AP MAC=... MAC SRC=...`, не перевірялося. Якщо подій Omada немає взагалі, перевірте спершу це (заявка A6).

## 9. Перший запуск: очікуйте хвилю алертів 100506

Правило 100506 (level 7) спрацьовує **один раз на кожен MAC**, якого немає в `known-macs` (Wazuh пам'ятає "вперше побачені" MAC на менеджері).
Одразу після встановлення кожен пристрій у мережі "новий", тому ви отримаєте **по одному алерту на кожен пристрій**. Це нормально.

Що робити:

1. Дайте системі попрацювати день-два.
2. Побудуйте таблицю пристроїв з алертів 100506/100507 (розділ 6).
3. Занесіть упізнані пристрої в `known-macs`: `"aa:bb:cc:dd:ee:ff":назва`, і видаліть рядок-заглушку.
4. Завантажте список і зробіть рестарт (розділ 7.3; поєднуйте з іншими оновленнями списків).

Далі алертитимуть лише справді нові пристрої. 100507 позначає пристрої з **рандомізованим (локально адмініструваним) MAC**
(друга шістнадцяткова цифра 2, 6, a або e), типово телефони з "приватною Wi-Fi адресою"; їх важко атрибутувати.

Примітка: найперший потік нового MAC потрапляє під 100506 і тому не проходить через правила за портами. Усі наступні проходять.

## 10. Тестування правил

Використовуйте інструмент дашборду **Ruleset Test** (*Server management* -> *Ruleset Test*, у старших версіях *Tools* -> *Ruleset Test*). Це той
самий рушій, що й `wazuh-logtest` на менеджері. Вставте рядок, запустіть, дивіться декодовані поля (phase 2) і правило, що спрацювало (phase 3).

Перед тестами занесіть тестового клієнта `00:11:22:33:44:66` у `known-macs` (інакше перший рядок дасть 100506) і зробіть рестарт.
Очікувані результати виведено з читання правил; підтвердьте їх на своєму менеджері.

## 11. Тюнінг і хибні спрацювання

Усе це робиться редагуванням `omada_rules.xml` (або власного файлу правил) у дашборді чи заявкою A5, а потім рестартом.

- **Ігри та медіа.** Правила 100730-100743 і 100850 інформаційні (level 3-5) і потрібні, щоб бачити, хто грає/стрімить.
  Якщо шум заважає, знизьте `level` до 0.
- **Порти спільні.** Правила "suspicious port" означають "часто використовується для", а не "є". Типові порушники: 9001 (Tor, але й Portainer та інші сервіси,
  level 10), 9999 / 7777 / 5555 (stratum майнінгу, але й ігрові сервери та Android ADB, level 10), 8000-8011 (Parsec, але й dev web-сервери, level 7),
  9000 (медіа Webex, але й багато dev-інструментів), 7000 (альтернативний IRC, але й AirPlay / Cassandra).
- **Заглушити відомо-безпечний випадок**: додайте правило, що перекриває шумне, наприклад у власному файлі `local_rules.xml`:

```xml
<rule id="100900" level="0">
  <if_sid>100522</if_sid>
  <field name="omada.src_mac">^00:11:22:33:44:66$</field>
  <description>Omada: ignore game server ports from the console 00:11:22:33:44:66</description>
</rule>
```

- **`ignore`.** `<rule ... ignore="600">` (як у 100505) придушує повтори алерта на N секунд. Використовуйте на балакучих правилах.
- **Рівні.** Змінюйте `level="N"` під свою політику. Кореляційні правила тримайте вище за правила, які вони рахують.
- **Неробочий час.** 100630-100633 повторно алертять ту саму подію з вищим level для будь-якого правила з груп `remote_access` / `vpn`, а до групи
  `remote_access` входить і внутрішній SSH (100805), тож внутрішній SSH уночі дасть level 10. Скоригуйте або приберіть, якщо це небажано.
  Часове вікно `20:00 - 07:00` жорстко задане в правилах.
- **Внутрішні діапазони.** `private-ips` не покриває решту multicast (`239.x`, наприклад SSDP) та CGNAT (`100.64.`). Додайте, якщо заважають.
- **Telegram**: підмережі беруться з https://core.telegram.org/resources/cidr.txt; час від часу звіряйте з `telegram-ips`.

## 12. Обмеження і що перевірити в logtest

Обмеження:

- У логу **немає лічильників байтів** і **немає вердикту allow/deny**: обсяг даних і те, чи заблокував фаєрвол потік, побачити не можна.
- **Порт не дорівнює застосунку.** Правила за портами кажуть "часто використовується для X". На 443 чи 51413 може працювати що завгодно.
- **Мости Tor (bridges) не виявляються.** У списку лише публічні реле з Onionoo; мости приватні за задумом.
- Списки threat intel настільки свіжі, наскільки свіже їхнє останнє оновлення (ручне чи автоматичне).
- Omada логує потік, а не вміст: збіг це підстава для розслідування, а не доказ компрометації.

Перевірте в *Ruleset Test* (залежить від версії Wazuh), перш ніж довіряти правилам:

1. **FTS на динамічному полі.** Декодер використовує `<fts>omada.src_mac</fts>` на обох дочірніх `omada-flow`. Протестуйте рядок із невідомим MAC двічі
   в одній сесії: перший має дати 100506/100507, другий ні.
2. **Обидва дочірні декодери працюють.** Для рядка **з** префіксом `[epoch]` phase 2 має показати `omada.epoch` **і** `omada.ap_mac`, `srcip`, `dstport` тощо.
   Якщо витягується лише одна група полів, дочірні декодери з однаковим ім'ям на вашій версії не виконуються обидва.
3. **`negate` на `dstport`** у частотному правилі 100620 (200+ подій за хвилину, крім 80, 443, 53, 123).
4. **`same_*` / `different_*` / `same_field`** у кореляційних правилах 100600-100604, 100850. Однорядкові тести їх не запустять;
   стежте за 100600 (сканування портів) після дозволеного сканування з тестового пристрою, узгодженого з мережевою командою.
5. **Пошук CDB за префіксом.** `address_match_key` із записами типу `10.:` / `192.168.:` має вважати `10.1.2.3` внутрішньою (тести 4 і 5).
   Якщо ваша версія приймає лише повні IP/CIDR, перепишіть `private-ips` і `telegram-ips` у форматі CIDR (`10.0.0.0/8:` тощо).
6. **Події level 0 у кореляції.** Правила 100600, 100620, 100621 рахують групу `omada`, до якої входять події level 0. Переконайтеся, що вони враховуються.

## 13. Troubleshooting

**Подій Omada немає взагалі.**

1. Запитайте **заявкою A6**, чи пишеться `/var/log/omada/omada.log`, і попросіть кілька рядків-зразків.
2. Вставте рядок-зразок у *Ruleset Test*. Якщо phase 2 не показує декодер `omada`: чи містить рядок `#012` (розділ 5.1)? Чи починається
   він із пробілу? Пробіл на початку ламає `^\[` декодера epoch; адмін побачить це через `head -3 /var/log/omada/omada.log | cat -A`.
3. Перевірте, що блок `<localfile>` є в конфігурації (розділ 5.2).

**Правило не спрацьовує.**

1. Правило має level 0-2? Такі в дашборді не з'являються; рівні дивіться в таблиці вище.
2. Чи не спрацювало **інше** правило раніше? Перемагає лише перше правило серед сусідніх; наприклад невідомий MAC дає 100506, а вночі 100630 замінює 100530.
3. Пам'ять "вперше побачено": MAC, який уже бачили, не викличе 100506 знову; для повторного тесту беріть новий MAC.
4. Правила threat intel не спрацюють, поки списки `ti-*` містять лише заглушку (розділ 7).

**Список не підхопився.**

- Він має бути зареєстрований через `<list>` всередині `<ruleset>` в `ossec.conf`, зі шляхом `etc/lists/<назва>` (без розширення), і
  назва списку в дашборді має бути саме такою.
- Формат: один `ключ:значення` на рядок, MAC-ключі в лапках, переноси LF, без порожнього файлу, без склеєних рядків (відсутній перенос колись склеїв `172.31.:` і `192.168.:`).
- Списки компілюються під час старту: чи був рестарт після зміни?

**Менеджер не перезапускається / дашборд показує помилку конфігурації.** Попросіть **заявкою A7** результат перевірки і лог менеджера. Типові причини:

- `Invalid ... XML` / `Syntax error`: зламаний коментар або тег, наприклад видалено лише один із двох рядків `ENABLE-100505` (розділ 8).
- `Rule ID ... already exists` / `Duplicate`: інші власні правила використовують ті самі ID; перенумеруйте.
- `Could not open CDB ...` / `list not found`: назва в `<list>` або в правилі відрізняється від справжньої назви списку.
- `Invalid element in the configuration`: рядки `<list>` стоять поза `<ruleset>`.

**Автоматичне оновлення (якщо встановлене) не оновлює списки.** Попросіть в адміна
`journalctl -u omada-ti-fetch -u omada-ti-apply --since "2 days ago"`. `WARN download failed` означає, що менеджер не досягає джерела
(фаєрвол / проксі); `REJECT` означає, що список мав неочікуваний формат і не був встановлений; `configuration check failed` означає, що
списки відкочено і Wazuh не перезапускався.

## 14. Обслуговування: як оновлювати все вручну

Усе тут робиться без жодного скрипта, через дашборд або заявку. Збирайте зміни і застосовуйте їх **одним рестартом**
в узгоджене тихе вікно: CDB-списки компілюються лише під час старту.

| Що | Джерело | Як часто | Як |
|---|---|---|---|
| `ti-feodo-c2`, `ti-tor-relays`, `ti-mining-pools` | Feodo, Onionoo, `docs/mining-pools.txt` | Раз на 1-2 тижні (пули щомісяця), або автоматично (7.4) | Розділ 7.1-7.3 |
| `telegram-ips` | https://core.telegram.org/resources/cidr.txt | Раз на кілька місяців | Команда нижче, далі *CDB lists* або заявка A5 |
| `known-macs` | Ваші пристрої, алерти нових пристроїв 100506/100507 | Коли з'являються нові легітимні пристрої | Розділ 9; *CDB lists* або A5 |
| `known-aps` (лише якщо 100505 увімкнене) | Ваші AP | До додавання або заміни AP | Розділ 8 |
| `private-ips` | Ваш адресний план | Коли змінюється адресний план | Редагувати список (`префікс.:` на рядок); *CDB lists* або A5 |
| `docs/mining-pools.txt` | Власні дослідження | Зрідка | Відредагувати, потім перезібрати `ti-mining-pools` (7.1); з автооновленням редагувати `/etc/omada-ti/mining-pools.txt` (заявка A5) |
| Правила і декодер (нова версія цього репозиторію) | Цей репозиторій | Коли змінюється | Замінити вміст `omada_rules.xml` / `omada_decoders.xml` у *Rules* / *Decoders*, або A5 |
| Ваш власний тюнінг | Ви | За потреби | Тримайте його в окремому файлі, наприклад `local_rules.xml` (розділ 11), щоб новий `omada_rules.xml` його не перезаписав |

**`telegram-ips` з офіційного списку CIDR** (кожна IPv4-мережа /16-/24 стає рядками `a.b.c.:`, по одному на кожну /24):

```bash
curl -fsS https://core.telegram.org/resources/cidr.txt | tr -d '\r' \
  | grep -E '^([0-9]{1,3}\.){3}[0-9]{1,3}/(1[6-9]|2[0-4])$' \
  | awk -F'[./]' '{n=2^(24-$5); for(i=0;i<n;i++) printf "%s.%s.%d.:\n",$1,$2,$3+i}' | sort -u > telegram-ips
wc -l telegram-ips     # десятки рядків; перед завантаженням порівняйте з поточним списком
```

PowerShell (у цьому репозиторії не тестувалося; перевірте, що результат виглядає як `91.108.56.:`):

```powershell
$lines = (Invoke-WebRequest -UseBasicParsing 'https://core.telegram.org/resources/cidr.txt').Content -split "`r?`n" |
  ForEach-Object {
    $m = [regex]::Match($_, '^(\d+)\.(\d+)\.(\d+)\.\d+/(1[6-9]|2[0-4])$')
    if ($m.Success) {
      $n = [math]::Pow(2, 24 - [int]$m.Groups[4].Value)
      0..($n - 1) | ForEach-Object { '{0}.{1}.{2}.:' -f $m.Groups[1].Value, $m.Groups[2].Value, ([int]$m.Groups[3].Value + $_) }
    }
  } | Sort-Object -Unique
[IO.File]::WriteAllText("$PWD\telegram-ips", (($lines -join "`n") + "`n"))
```

**Не публікуйте власні списки.** `known-macs` і `known-aps` зі справжніми MAC (і справжній `private-ips`) описують вашу мережу.
Якщо тримаєте їх під контролем версій, використовуйте приватний репозиторій, а не цей публічний.
