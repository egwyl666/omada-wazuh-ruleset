# Omada -> Wazuh ruleset

[English version: README.md](README.md)

Правила виявлення для логів клієнтського трафіку **TP-Link Omada** (точки доступу EAP / контролер) у **Wazuh SIEM**.
Omada пише по одному запису на кожен мережевий потік. Цей проєкт декодує такі записи і перетворює їх на алерти:
підозрілі порти, збіги з threat intel, невідомі пристрої, латеральний рух із Wi-Fi, сканування, віддалений доступ у неробочий час тощо.

Структура репозиторію:

| Шлях | Що це |
|---|---|
| `decoders/omada_decoders.xml` | Декодер: розбирає рядок логу на поля |
| `rules/omada_rules.xml` | 86 активних правил (+ 1 вимкнене, 100505), ID 100500-100850 |
| `lists/private-ips`, `lists/telegram-ips` | CDB-списки: внутрішні префікси, підмережі Telegram |
| `lists/known-macs`, `lists/known-aps` | CDB-списки: дозволені клієнтські пристрої та точки доступу (заповнюєте ви; `known-aps` опційний) |
| `lists/mining-pools.txt` | Вхідні дані для скрипта (домени майнінг-пулів); **не** CDB-список |
| `scripts/update_ti_lists.sh` | Збирає CDB-списки threat intel: `ti-feodo-c2`, `ti-tor-relays`, `ti-mining-pools` |
| `docs/CHANGELOG_UA.md` | Історія змін (українською) |

> Важливо: правила написано за описом формату логів Omada. Перш ніж покладатися на них у production, виконайте перевірки з
> [розділу 10](#10-тестування-через-wazuh-logtest) та [розділу 12](#12-обмеження-і-що-перевірити-в-logtest) на своєму менеджері.

## 1. Що це і навіщо

Omada дає IP джерела й призначення, порти, протокол та MAC клієнта і AP. Вона **не** дає вміст пакетів, байти, URL та
вердикт allow/deny. Тому виявлення будується на тому, **хто, з ким, на який порт, як часто і коли** спілкується.

| Група | ID правил | Level | Що виявляє |
|---|---|---|---|
| Базове | 100500 | 0 | Будь-який декодований потік Omada (батько всіх правил) |
| Інвентаризація | 100505 (вимк.), 100506, 100507 | 10 / 7 / 7 | Невідома AP (вимкнено за замовчуванням), новий невідомий пристрій, новий пристрій із рандомізованим MAC |
| Поділ за призначенням | 100510, 100511 | 0 | Зовнішнє чи внутрішнє призначення (через `private-ips`) |
| Threat intel | 100512-100514 | 12 / 10 / 10 | Призначення: відомий C2 ботнету (Feodo), реле Tor або майнінг-пул |
| Анонімайзери / C2 / майнери (порти) | 100520-100524 | 10, 10, 10, 8, 6 | Порти Tor, reverse shell/C2, stratum майнінгу, IRC, SOCKS/HTTP-проксі |
| Віддалений доступ (зовнішній) | 100530-100534 | 8, 8, 9, 4, 7 | Вихідні RDP, VNC, Telnet, SSH, TeamViewer/AnyDesk/RustDesk |
| Ризиковані протоколи (зовнішні) | 100540-100545 | 9, 8, 5, 8, 7, 6 | SMB/NetBIOS/RPC, прямий SMTP, FTP, TFTP, SNMP/LDAP, порти баз даних в інтернет |
| Обхід DNS | 100550-100551 | 4, 5 | Прямий DNS на зовнішні резолвери, DNS-over-TLS |
| VPN / тунелі | 100560 | 5 | OpenVPN, WireGuard, PPTP, L2TP, IPsec |
| P2P / торрент | 100570-100571 | 5 | Порти призначення / джерела BitTorrent |
| Латеральний рух (внутрішній) | 100590-100596 | 6, 6, 8, 6, 6, 7, 7 | Wi-Fi клієнт до SMB, RDP, WinRM, RPC, VNC, Telnet, баз даних |
| Кореляція | 100600-100604 | 10, 12, 8, 12, 10 | Сканування портів, внутрішній sweep, підтверджений торрент, повторний трафік до C2/майнерів, спамбот |

| Застосунки (зовнішні) | 100700-100754 | 0-7 | Web, Telegram, push, дзвінки, ігри, стрімінг, sync, IoT, віддалений робочий стіл. Здебільшого level 0-4 (видимість), 100754 має 7 |
| Шум LAN (внутрішній) | 100800-100806 | 0 (100805: 3) | DNS/DHCP/Kerberos, mDNS/SSDP, друк, AirPlay, внутрішній web, SSH, Syncthing |

Правила level 0 алертів не створюють; вони лише класифікують подію, щоб на них могли спиратися інші правила.

## 2. Вимоги

- **Wazuh manager 4.3 або новіший** (декодер використовує PCRE2; кореляція використовує `same_field` / `different_*`).
- **Логи Omada через syslog.** Налаштуйте контролер / точки доступу Omada на відправку логів на віддалений syslog-сервер
  (назва меню залежить від версії Omada, шукайте "remote logging" / "syslog server"). У цій інструкції приймач syslog це
  **rsyslog на менеджері Wazuh**, який пише у файл, що читає Wazuh.
- Для `update_ti_lists.sh` на менеджері: `bash`, `curl`, `getent` (пакет `libc-bin`, зазвичай уже є), root, `systemctl`.
- Годинник і часовий пояс менеджера мають бути правильні (правила неробочого часу беруть локальний час менеджера).

## 3. Приклад логу та розбір полів

```
[1791521490.308231667] AP MAC=00:11:22:33:44:55 MAC SRC=00:11:22:33:44:66 IP SRC=192.0.2.40 IP DST=149.154.167.41 IP proto=6 SPT=55138 DPT=443
```

| Поле Wazuh | Звідки | Приклад | Значення |
|---|---|---|---|
| `omada.epoch` | `[...]` | `1791521490.308231667` | Unix-час із дробовою частиною. Необов'язкове: є не в кожному записі |
| `omada.ap_mac` | `AP MAC=` | `00:11:22:33:44:55` | Точка доступу, через яку пройшов трафік |
| `omada.src_mac` | `MAC SRC=` | `00:11:22:33:44:66` | Клієнтський пристрій (ключ для інвентаризації та P2P-кореляції) |
| `srcip` | `IP SRC=` | `192.0.2.40` | IP клієнта |
| `dstip` | `IP DST=` | `149.154.167.41` | IP призначення |
| `protocol` | `IP proto=` | `6` | Номер IP-протоколу: 6 = TCP, 17 = UDP |
| `srcport` | `SPT=` | `55138` | Порт джерела (зазвичай ефемерний) |
| `dstport` | `DPT=` | `443` | Порт призначення; на нього спираються більшість правил |

Власні поля в алертах мають вигляд `data.omada.src_mac`, `data.srcip`, `data.dstport` тощо.

## 4. Встановлення покроково

Виконуйте на **менеджері** Wazuh від root. Шляхи стандартні для типової інсталяції.

```bash
# 1. Декодер і правила
cp decoders/omada_decoders.xml /var/ossec/etc/decoders/
cp rules/omada_rules.xml       /var/ossec/etc/rules/

# 2. CDB-списки (+ список доменів пулів для скрипта)
cp lists/private-ips lists/telegram-ips lists/known-macs lists/known-aps lists/mining-pools.txt /var/ossec/etc/lists/

# 3. Скрипт threat intel
cp scripts/update_ti_lists.sh /usr/local/bin/
chmod +x /usr/local/bin/update_ti_lists.sh

# 4. Один раз згенерувати ti-* списки (поки без --restart)
/usr/local/bin/update_ti_lists.sh

# 5. Власник
chown wazuh:wazuh /var/ossec/etc/decoders/omada_decoders.xml /var/ossec/etc/rules/omada_rules.xml
chown wazuh:wazuh /var/ossec/etc/lists/*
```

Крок 6: зареєструйте списки в `/var/ossec/etc/ossec.conf` **всередині наявного блоку `<ruleset>`**
(`mining-pools.txt` не додавайте: це не CDB-список):

```xml
<ruleset>
  <!-- ...наявні записи... -->
  <list>etc/lists/private-ips</list>
  <list>etc/lists/telegram-ips</list>
  <list>etc/lists/known-macs</list>
  <list>etc/lists/known-aps</list>
  <list>etc/lists/ti-feodo-c2</list>
  <list>etc/lists/ti-tor-relays</list>
  <list>etc/lists/ti-mining-pools</list>
</ruleset>
```

Крок 7: перевірте конфігурацію і перезапустіть.

```bash
/var/ossec/bin/wazuh-analysisd -t        # перевірка конфігурації / правил, помилок бути не повинно
systemctl restart wazuh-manager
```

ID правил 100500-100850 не повинні збігатися з вашими іншими власними правилами; якщо збігаються, змініть їх.

## 5. Приймання логів: rsyslog -> файл -> Wazuh

### 5.1 rsyslog

Створіть `/etc/rsyslog.d/10-omada.conf`:

```
# НЕ перетворювати керівні символи на #015 / #012 (див. нижче)
global(parser.escapeControlCharactersOnReceive="off")

module(load="imudp")
input(type="imudp" port="514" ruleset="omada")
# Для TCP замість UDP або разом із ним:
# module(load="imtcp")
# input(type="imtcp" port="514" ruleset="omada")

template(name="omada_raw" type="string" string="%msg%\n")

ruleset(name="omada") {
    action(type="omfile" file="/var/log/omada/omada.log" template="omada_raw")
    stop
}
```

```bash
mkdir -p /var/log/omada
systemctl restart rsyslog
# фаєрвол має пропускати UDP/TCP 514 від контролера / AP Omada
```

Додайте також правило logrotate для `/var/log/omada/omada.log` (інакше файл рости без обмежень).

**Проблема `#015#012`.** Omada може пакувати кілька записів в одне syslog-повідомлення, розділяючи їх CR+LF.
За замовчуванням rsyslog екранує керівні символи, тому роздільники стають буквальним текстом `#015#012` (вісімкове 015 = CR, 012 = LF),
і Wazuh бачить один величезний рядок зі склеєними записами; декодується тільки перший запис.
`parser.escapeControlCharactersOnReceive="off"` вимикає екранування, тож у файлі з'являються справжні переноси рядків і кожен запис
стає окремим рядком. Після зміни `grep -c '#012' /var/log/omada/omada.log` має перестати рости.

### 5.2 Wazuh `<localfile>`

У `/var/ossec/etc/ossec.conf` (на машині, де лежить файл; для окремого syslog-хоста встановіть там агент Wazuh):

```xml
<localfile>
  <log_format>syslog</log_format>
  <location>/var/log/omada/omada.log</location>
</localfile>
```

Після цього перезапустіть: `systemctl restart wazuh-manager` (або `wazuh-agent`).

## 6. Як знайти все, що потрібно

**Де логи Omada на сервері?** Це файл, який ви вказали в rsyslog (`/var/log/omada/omada.log` вище).
Якщо налаштовував хтось інший, знайдіть його:

```bash
grep -rl 'AP MAC=' /var/log 2>/dev/null | head
```

**MAC власних AP** (опційно, потрібні лише для правила 100505; див. [розділ 8](#8-точки-доступу-known-aps-і-правило-100505-опційно-вимкнено-за-замовчуванням)):

```bash
grep -oE 'AP MAC=[^ ]+' /var/log/omada/omada.log | sort | uniq -c
```

**MAC клієнтських пристроїв** (законні занесіть у `known-macs`):

```bash
grep -oE 'MAC SRC=[^ ]+' /var/log/omada/omada.log | sort | uniq -c
```

**Формат запису в CDB.** Один запис на рядок, MAC у подвійних лапках (у ньому є двокрапки), далі `:` і мітка:

```
"aa:bb:cc:dd:ee:ff":my-laptop
```

MAC у логах у нижньому регістрі; у списках теж пишіть у нижньому (пошук чутливий до регістру).
CDB-файл не може бути порожнім. У `known-macs` і `known-aps` лежить заглушка `"00:00:00:00:00:00":placeholder-replace-me`.

**Де що лежить?**

| Що | Шлях |
|---|---|
| Головний конфіг | `/var/ossec/etc/ossec.conf` |
| Власні правила | `/var/ossec/etc/rules/` |
| Власні декодери | `/var/ossec/etc/decoders/` |
| CDB-списки | `/var/ossec/etc/lists/` |
| Лог менеджера (помилки старту) | `/var/ossec/logs/ossec.log` |
| Алерти (JSON) | `/var/ossec/logs/alerts/alerts.json` |

**Часовий пояс менеджера** (потрібен правилам неробочого часу 100630-100633: вони беруть локальний час менеджера і написані під `Europe/Kyiv`, раніше `Europe/Kiev`):

```bash
timedatectl | grep 'Time zone'
date
# за потреби змінити:
timedatectl set-timezone Europe/Kyiv
systemctl restart wazuh-manager
```

**Де дивитися алерти.**

- Дашборд: *Threat Hunting / Security events*. Корисні фільтри: `rule.groups: suspicious_port`, `threat_intel`, `inventory`, `new_device`,
  `off_hours`, `lateral`, `scan`, `p2p`, `remote_access`, `policy_violation`, `anomaly`, `app_gaming`, або `rule.id: 100506`.
  Фільтр за пристроєм: `data.omada.src_mac: "00:11:22:33:44:66"`.
- Командний рядок:

```bash
tail -f /var/ossec/logs/alerts/alerts.json | jq -c 'select(.rule.id|startswith("1005") or startswith("1006"))'
jq -c 'select(.rule.groups|index("threat_intel")) | {t:.timestamp, id:.rule.id, src:.data.srcip, dst:.data.dstip}' /var/ossec/logs/alerts/alerts.json
```

Події level 0 в `alerts.json` не потрапляють. Щоб їх побачити, тимчасово ввімкніть `<logall_json>yes</logall_json>` у `<global>` і читайте `archives.json`.

## 7. Threat intel

`update_ti_lists.sh` збирає три CDB-списки, які використовують правила 100512-100514. Їх перевіряють **до** правил за портами.

| Список | Джерело | Правило | Level |
|---|---|---|---|
| `ti-feodo-c2` | abuse.ch Feodo Tracker, список "recommended" (C2 ботнетів, мало хибних спрацювань, CC0) | 100512 | 12 |
| `ti-tor-relays` | API Onionoo проєкту Tor, усі працюючі реле (не лише exit: клієнти підключаються до relay/guard) | 100513 | 10 |
| `ti-mining-pools` | домени з `mining-pools.txt`, що резолвляться в IP через `getent ahostsv4`; діапазони Cloudflare відкидаються (пул за CDN позначив би пів-інтернету) | 100514 | 10 |

Як працює скрипт:

1. Завантажує кожне джерело (`curl` з обмеженням часу) і витягує IPv4-адреси; перетворює їх на рядки `IP:назва-списку`.
2. Перевірка адекватності: якщо список вийшов меншим за очікуване (Tor: менше 1000), завантаження вважається зламаним і **лишається старий список**.
3. Замінює файл лише якщо вміст змінився (`cmp`), власник `wazuh:wazuh`, права 660 (змінні `LISTS` і `OWNER` можна перевизначити).
4. З `--restart` перезапускає `wazuh-manager` **лише якщо щось змінилося**.

Використання і cron. Створіть `/etc/cron.d/omada-ti`:

```
15 4 * * * root /usr/local/bin/update_ti_lists.sh --restart >> /var/log/update_ti_lists.log 2>&1
```

Домени майнінг-пулів додавайте/видаляйте в `/var/ossec/etc/lists/mining-pools.txt` (по одному в рядок, `#` для коментарів).

**Чому рестарт і чому вночі.** Wazuh компілює CDB-списки лише під час старту менеджера, тож нові дані не діють до перезапуску.
Рестарт ненадовго зупиняє аналіз подій і скидає лічильники кореляційних правил у пам'яті (сканування, торрент, спамбот, частота);
вночі, коли трафіку найменше, це коштує найменше. Не запускайте скрипт із `--restart` у робочий час.

## 8. Точки доступу (`known-aps`) і правило 100505: опційно, вимкнено за замовчуванням

**Що таке `known-aps`.** Білий список MAC **точок доступу**: значення `AP MAC=` у логу, тобто EAP, через яку пройшов трафік клієнта.
Це **не** список контролерів. Контролер Omada (software controller, OC200/OC300) лише керує AP і пересилає їхні логи;
його власний MAC ніколи не з'являється в `AP MAC=`, тому контролер у цей список не заносять.

**Хто його використовує.** Лише правило 100505 (rogue AP, level 10): "цей потік пройшов через AP, якої немає в `known-aps`". Жодне інше правило список не читає.

**Чи працює воно зараз? Ні, і від нього нічого не залежить.** 100505 закоментоване, тож список не перевіряється. У репозиторії
`known-aps` містить заглушку (`"00:00:00:00:00:00":placeholder-replace-me`) лише для того, щоб запис `<list>etc/lists/known-aps</list>` в
`ossec.conf` вказував на наявний непорожній файл. Усі інші правила (порти, threat intel, інвентаризація нових пристроїв 100506/100507,
кореляція, неробочий час) працюють, не знаючи жодної AP. **Встановлюйте все за розділом 4 і залиште `known-aps` як є.**

**Чому вимкнено за замовчуванням.** Якби 100505 було ввімкнене з порожнім або неповним списком, під нього потрапляв би **кожен потік** через "невідому" AP.
Оскільки перемагає лише перше правило серед сусідніх (100505 перевіряється до поділу за призначенням), такі потоки ще й перестали б
доходити до правил за портами і threat intel. Тому вмикайте його лише з повним списком, а нові AP додавайте до списку **до** їх запуску.

### Підключення AP пізніше

1. **Знайдіть MAC AP.** Підійде будь-який спосіб; доступ до контролера не обов'язковий:
   - з логів, які Wazuh уже отримує (один рядок на AP, число показує, скільки потоків через неї пройшло):

     ```bash
     grep -oE 'AP MAC=[^ ]+' /var/log/omada/omada.log | sort | uniq -c
     ```

   - з інтерфейсу контролера Omada, список *Devices* (колонка MAC), якщо маєте до нього доступ;
   - з наліпки на самій AP.

   MAC із логів, який не вдається зіставити зі справжньою AP, це саме те, що правило має ловити: розберіться з ним, перш ніж додавати.

2. **Складіть список.** Згенеруйте чернетку з логів, потім дайте кожній AP зрозумілу назву і видаліть рядок-заглушку:

   ```bash
   grep -oE 'AP MAC=[^ ]+' /var/log/omada/omada.log | cut -d= -f2 | tr 'A-F' 'a-f' | sort -u \
     | awk '{printf "\"%s\":ap-%02d\n", $1, NR}' > /tmp/known-aps
   cat /tmp/known-aps
   ```

   Результат (назви відредагуйте вручну):

   ```
   "aa:bb:cc:dd:ee:01":office-floor1
   "aa:bb:cc:dd:ee:02":office-floor2
   ```

3. **Встановіть список:**

   ```bash
   cp /tmp/known-aps /var/ossec/etc/lists/known-aps
   chown wazuh:wazuh /var/ossec/etc/lists/known-aps
   ```

4. **Увімкніть правило.** Правило загорнуте в коментар, перший і останній рядки якого мають маркер `ENABLE-100505`. Видаліть ці два рядки:

   ```bash
   cp /var/ossec/etc/rules/omada_rules.xml /root/omada_rules.xml.bak
   sed -i '/ENABLE-100505/d' /var/ossec/etc/rules/omada_rules.xml
   ```

5. **Перевірте і перезапустіть:** `/var/ossec/bin/wazuh-analysisd -t`, потім `systemctl restart wazuh-manager`.

6. **Перевірте у `wazuh-logtest`:** рядок з `AP MAC=`, що є в `known-aps`, **не** має давати 100505; той самий рядок з будь-яким іншим MAC AP
   має давати 100505, level 10.

**Додати AP пізніше:** додайте її рядок у `known-aps`, `chown`, рестарт (списки компілюються під час старту), потім вмикайте AP.
**Вимкнути знову:** відновіть резервну копію (`cp /root/omada_rules.xml.bak /var/ossec/etc/rules/omada_rules.xml`) або скопіюйте файл із цього репозиторію, потім рестарт.

> Примітка: логи потоків, на яких побудовано правила, зібрано через контролер Omada. Чи надсилають AP у standalone-режимі (без контролера)
> такі самі записи `AP MAC=... MAC SRC=...`, не перевірялося. Якщо `grep 'AP MAC=' /var/log/omada/omada.log` нічого не знаходить, декодер не спрацює.

## 9. Перший запуск: очікуйте хвилю алертів 100506

Правило 100506 (level 7) спрацьовує **один раз на кожен MAC**, якого немає в `known-macs` (пам'ять "вперше побачено" Wazuh зберігає в `/var/ossec/queue/fts/`).
Одразу після встановлення кожен пристрій у мережі "новий", тому ви отримаєте **по одному алерту на кожен пристрій**. Це нормально.

Що робити:

1. Дайте системі попрацювати день-два.
2. Перегляньте алерти 100506/100507 (або виконайте команду для `MAC SRC=` з розділу 6).
3. Занесіть упізнані пристрої в `known-macs`: `"aa:bb:cc:dd:ee:ff":назва`.
4. `chown wazuh:wazuh /var/ossec/etc/lists/known-macs && systemctl restart wazuh-manager`.

Далі алертитимуть лише справді нові пристрої. 100507 позначає пристрої з **рандомізованим (локально адмініструваним) MAC**
(друга шістнадцяткова цифра 2, 6, a або e), типово телефони з "приватною Wi-Fi адресою"; їх важко атрибутувати.

Примітка: найперший потік нового MAC потрапляє під 100506 і тому не проходить через правила за портами. Усі наступні проходять.

## 11. Тюнінг і хибні спрацювання

- **Ігри та медіа.** Правила 100730-100743 і 100850 інформаційні (level 3-5) і потрібні, щоб бачити, хто грає/стрімить.
  Якщо шум заважає, знизьте `level` до 0 або приберіть правило з файлу.
- **Порти спільні.** Правила "suspicious port" означають "часто використовується для", а не "є". Типові порушники: 9001 (Tor, але й Portainer та інші сервіси,
  level 10), 9999 / 7777 / 5555 (stratum майнінгу, але й ігрові сервери та Android ADB, level 10), 8000-8011 (Parsec, але й dev web-сервери, level 7),
  9000 (медіа Webex, але й багато dev-інструментів), 7000 (альтернативний IRC, але й AirPlay / Cassandra).
- **Заглушити відомо-безпечний випадок**: додайте правило, що перекриває шумне, наприклад у `/var/ossec/etc/rules/local_rules.xml`:

```xml
<rule id="100900" level="0">
  <if_sid>100522</if_sid>
  <field name="omada.src_mac">^00:11:22:33:44:66$</field>
  <description>Omada: ignore game server ports from the console 00:11:22:33:44:66</description>
</rule>
```

- **`ignore`.** `<rule ... ignore="600">` (як у 100505) придушує повтори алерта на N секунд. Використовуйте на балакучих правилах.
- **Рівні.** Змінюйте `level="N"` під свою політику. Кореляційні правила тримайте вище за правила, які вони рахують.
- **Неробочий час.** 100630-100633 повторно алертять ту саму подію з вищим level для будь-якого правила з груп `remote_access` / `vpn`, а до групи
  `remote_access` входить і внутрішній SSH (100805), тож внутрішній SSH уночі дасть level 10. Скоригуйте або приберіть, якщо це небажано.
  Часове вікно `20:00 - 07:00` жорстко задане в правилах.
- **Внутрішні діапазони.** `private-ips` не покриває решту multicast (`239.x`, наприклад SSDP) та CGNAT (`100.64.`). Додайте, якщо заважають.
- **Telegram**: підмережі беруться з https://core.telegram.org/resources/cidr.txt; час від часу оновлюйте `telegram-ips`.

## 12. Обмеження і що перевірити в logtest

Обмеження:

- У логу **немає лічильників байтів** і **немає вердикту allow/deny**: обсяг даних і те, чи заблокував фаєрвол потік, побачити не можна.
- **Порт не дорівнює застосунку.** Правила за портами кажуть "часто використовується для X". На 443 чи 51413 може працювати що завгодно.
- **Мости Tor (bridges) не виявляються.** У списку лише публічні реле з Onionoo; мости приватні за задумом.
- Списки threat intel настільки свіжі, наскільки свіжий останній запуск скрипта, а пул за CDN чи спільна IP-адреса можуть давати хибні спрацювання.
- Omada логує потік, а не вміст: збіг це підстава для розслідування, а не доказ компрометації.

Перевірте в `wazuh-logtest` (залежить від версії Wazuh), перш ніж довіряти правилам:

1. **FTS на динамічному полі.** Декодер використовує `<fts>omada.src_mac</fts>` на обох дочірніх `omada-flow`. Відправте рядок із невідомим MAC двічі в одній
   сесії logtest: перший має дати 100506/100507, другий ні.
2. **Обидва дочірні декодери працюють.** Для рядка **з** префіксом `[epoch]` Phase 2 має показати `omada.epoch` **і** `omada.ap_mac`, `srcip`, `dstport` тощо.
   Якщо витягується лише одна група полів, дочірні декодери з однаковим ім'ям на вашій версії не виконуються обидва.
3. **`negate` на `dstport`** у частотному правилі 100620 (200+ подій за хвилину, крім 80, 443, 53, 123).
4. **`same_*` / `different_*` / `same_field`** у кореляційних правилах 100600-100604, 100850 (згенеруйте тестовий трафік: 25+ портів за 60 с мають дати 100600).
5. **Пошук CDB за префіксом.** `address_match_key` із записами типу `10.:` / `192.168.:` має вважати `10.1.2.3` внутрішньою. Якщо ваша версія приймає лише
   повні IP/CIDR, перепишіть `private-ips` і `telegram-ips` у форматі CIDR (`10.0.0.0/8:` тощо).
6. **Події level 0 у кореляції.** Правила 100600, 100620, 100621 рахують групу `omada`, до якої входять події level 0. Переконайтеся, що вони враховуються.

## 13. Troubleshooting

**Правило не спрацьовує.**

1. Чи доходить лог до Wazuh? `tail -f /var/log/omada/omada.log` і `grep omada /var/ossec/logs/ossec.log`.
2. Чи декодується рядок? Вставте його в `wazuh-logtest -v`. Якщо Phase 2 не показує декодер `omada`, перевірте, що записи справді по одному в рядку
   (розділ 5, `#012`) і що рядок не починається з пробілу: `head -3 /var/log/omada/omada.log | cat -A`; пробіл на початку ламає `^\[` декодера epoch.
3. Чи правило level 0? Правила level 0 ніколи не алертять; рівні дивіться в таблиці вище.
4. Чи не спрацювало **інше** правило раніше? Перемагає лише перше правило серед сусідніх; наприклад невідомий MAC дає 100506, а вночі 100630 замінює 100530.
5. Пам'ять "вперше побачено": MAC, який уже бачили, не викличе 100506 знову; для повторного тесту беріть новий MAC.

**Список не підхопився.**

- Він має бути зареєстрований через `<list>` в `ossec.conf` всередині `<ruleset>`, зі шляхом `etc/lists/<назва>` (без розширення).
- Власник: `chown wazuh:wazuh /var/ossec/etc/lists/*`.
- Формат: один `ключ:значення` на рядок, MAC-ключі в лапках, без порожнього файлу, без склеєних рядків (відсутній перенос колись склеїв `172.31.:` і `192.168.:`).
- Списки компілюються під час старту: `systemctl restart wazuh-manager`. Перевірте `grep -i cdb /var/ossec/logs/ossec.log`.
- Файлів `ti-*` не існує, доки ви один раз не запустите `update_ti_lists.sh`. Правило, що посилається на відсутній список, може завадити старту менеджера.

**Помилки під час старту менеджера.**

```bash
/var/ossec/bin/wazuh-analysisd -t
tail -50 /var/ossec/logs/ossec.log
```

- `Invalid ... XML` / `Syntax error`: зламаний коментар або тег, наприклад видалено лише один із двох рядків `ENABLE-100505` (див. розділ 8).
- `Rule ID ... already exists` / `Duplicate`: ваші інші власні правила використовують ті самі ID; перенумеруйте.
- `Could not open CDB ...` / `list not found`: назва файлу в `<list>` або в правилі відрізняється від справжньої, або файл не читається користувачем `wazuh`.
- `Invalid element in the configuration`: рядки `<list>` стоять поза `<ruleset>`.
- Проблеми зі скриптом: `tail /var/log/update_ti_lists.log`; `WARN ... keeping old list` означає, що завантаження не вдалося або список підозріло малий.
